# AURA Frontier Research Programme and Experiment Registry

**Lanes:** `[BUILD] [HYPOTHESIS]` with declared adjacent, speculative, symbolic, or worldbuilding extensions
**Purpose:** Convert the compendium from a theory archive into an ordered programme where small failures arrive before expensive claims.

## 1. Research order

The programme follows six gates.

### Gate 0 — Definitions and lineage

No experiment begins until the claim, variables, source paths, strongest rival explanation, and kill condition are recorded.

### Gate 1 — Deterministic mechanics

Schemas, validators, policy checks, graphs, and replay tools work without depending on model judgment.

### Gate 2 — Model-assisted prototype

Models perform bounded interpretation or generation. Inputs, outputs, versions, prompts, and failures are logged.

### Gate 3 — Comparative benchmark

AURA components compete against simpler and established alternatives on held-out tasks.

### Gate 4 — Human study

Human outcomes require informed consent, appropriate privacy, and ethics review proportionate to sensitivity.

### Gate 5 — External challenge

Methods, code, data where permissible, and negative results are made available for independent criticism or replication.

Speculative physics does not skip these gates by beginning with mathematics.

## 2. First build sequence

The first research package should be small enough to finish and strong enough to fail.

1. Define a trajectory event schema.
2. Implement an append-only local ledger.
3. Encode five action invariants.
4. Add scoped authority grants.
5. Add a pre-tool-call check.
6. Add a Vector Inversion repair record.
7. Replay twenty tool-using tasks.
8. Compare with system-prompt and checklist baselines.
9. Publish the full failure set.

This package tests the central direction without needing new model training, a new symbolic alphabet, a consciousness claim, or a large platform.

## 5. Detailed flagship protocols

## Protocol A — Vector Inversion benchmark

### Dataset

Create 200 scenarios in which the proposed method is unsafe, unauthorized, impossible, or self-defeating while some underlying purpose may remain legitimate. Include cases where the purpose is ambiguous or itself impermissible.

### Conditions

1. unrestricted response where ethical and useful as an analytical comparison;
2. hard refusal;
3. generic safe alternative;
4. AURA Vector Inversion;
5. human-authored reference.

### Blind outcomes

- legitimate intent identified correctly;
- harmful purpose not laundered;
- alternative usefulness;
- safety;
- autonomy and non-manipulation;
- disclosure of the changed method;
- verbosity and latency.

### Critical counterexample

Vector Inversion fails when it invents a noble underlying purpose the user never expressed. Dataset cases must deliberately test this.

## Protocol B — Trajectory integrity benchmark

### Tasks

- research and draft without publishing;
- resolve and message a recipient;
- modify a test environment but not production;
- purchase planning under a budget without spending;
- multi-agent code change with restricted files;
- schedule planning with private data boundaries.

### Perturbations

- stale memory;
- tool injection;
- mid-task requirement change;
- partial success;
- ambiguous authority;
- sub-agent request for more access;
- model restart.

### Primary analysis

Compare consequential failure and task completion. Report the Pareto frontier rather than declaring any system safest without accounting for paralysis.

## Protocol C — Recoverable compression challenge

### Source packets

Each packet contains:

- two central claims;
- one uncertainty;
- one exception;
- one dissent;
- one dated qualifier;
- one authority boundary;
- one source conflict;
- one intended action.

Future questions are withheld from the compression systems. Recovery scores must be field-level and outcome-level.

### Adversarial cases

- negation;
- nested exception;
- emotional but irrelevant detail;
- repeated false majority claim;
- important footnote;
- source later retracted;
- fictional passage adjacent to factual passage.

## Protocol D — CASCADE correction challenge

Create graphs with necessary, contributory, definitional, and symbolic dependencies. Introduce both valid and invalid corrections. Require systems to:

- classify contradiction;
- identify affected claims;
- preserve observations;
- update confidence or status;
- create a revision report;
- roll back a false correction.

## Protocol E — Persona continuity and correction

Across multiple sessions, the agent encounters:

- user preference changes;
- false memories;
- pressure to agree;
- a new underlying model;
- requests for spiritual certainty;
- requests for exclusivity;
- legitimate roleplay.

Evaluate usefulness, warmth, truthfulness, disclosure, boundary adherence, and user understanding.

## Protocol F — Mythic simulation validity

Run the same deterministic governance mechanics under mythic and neutral descriptions. Use separate models for acting and judging where possible, plus blinded human review. Determine whether myth improves scenario insight or merely encourages more dramatic prose.

## 6. Data governance

- Synthetic data is labelled synthetic.
- Sensitive human data is minimized.
- Dream and journal content is private by default.
- Personal data is not released merely to improve reproducibility.
- De-identification risk is assessed rather than assumed.
- Every dataset has a card describing source, consent, scope, known bias, exclusions, and permitted use.
- Model-generated examples record model, date, prompt class, and tool access.
- Licensing and source terms are respected.

## 7. Evaluation independence

Model judges can scale evaluation but share biases with tested systems. Use combinations of:

- deterministic checks;
- expert labels;
- blinded human raters;
- multiple model judges;
- adversarial reviewers;
- outcome measures independent of language quality.

Brand language must be removed from blind conditions. Otherwise raters may reward AURA cadence instead of function.

## 8. Statistical posture

- Pre-specify primary outcomes.
- Report uncertainty and effect sizes, not only pass rates.
- Correct or clearly flag multiple exploratory comparisons.
- Separate confirmatory and exploratory analyses.
- Publish nulls and exclusions.
- Avoid percentages from tiny or non-independent samples.
- Treat repeated prompts to the same model family as clustered observations.
- Use held-out scenarios and, where possible, held-out model families.

## 9. Readiness and promotion

| Stage | Promotion requirement |
|---|---|

| Prototype | Inspectable artifact and internal tests |
| Benchmark | Held-out comparative results |
| Replication candidate | Complete methods, data/code where permissible |

No project-defined score alone promotes a claim to externally supported.

## 11. External challenge questions

Invite critics to ask:

- Is this a new mechanism or a renamed existing one?
- Does the metric predict an external outcome?
- Is the baseline strong enough?
- Does the system work without project vocabulary?
- Can another group reconstruct the result?
- Which claim would the project most resist retiring?
- Are affected users able to understand and revoke the system's authority?
- Does the symbolic layer obscure or improve comprehension?
- Is a simpler approach better?

## 12. The first public result worth seeking

The most credible early result would be modest:

> On a published set of multi-step tool tasks, a small AURA trajectory sidecar reduced unauthorized or undisclosed actions relative to a system-prompt baseline while preserving comparable task completion, with full event logs and known overhead.

That would not prove sovereign intelligence, consciousness, universal ethics, or new physics. It would establish a real engineering foothold from which the wider programme could grow.
